# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Environment quirks

- The working directory still has its old name, `pocketbook-readtrack `, **with a trailing space**. Always quote paths. The project and its GitHub repo are `pocketbook-statistics`; only the local checkout lags behind.
- Git repo on `main`, remote `origin` → `winst0niuss/pocketbook-statistics`. History is short; the two `tmp:` commits were CI probes for the qmllint gate.

## Commands

```bash
make sdk      # one-time: sparse-clones fstanis/pocketbook-sdk-qt6 into third_party/ (~2 MB)
make qt       # cross-compiles in Docker -> build-qt/PocketBookStatistics.app (ARM32 softfp ELF)
make test     # host build+run of test/test_tracker.c (no device, no Docker)
make deploy   # cp to $(DEVICE)/applications/ (DEVICE defaults to /Volumes/NO NAME)
make icons    # regenerate qt/qml/*.bmp from tools/make_icon.py (needs Pillow)
make qmlcheck # tools/check_qml.py alone, without the C tests
```

`make test` is a single assert-based binary — there is no test selection or framework. To run one scenario, comment out the others in `main()` of `test/test_tracker.c` or add a new block. It compiles `src/tracker.c`, `src/stats_db.c`, `src/version.c`, `src/log.c` and `src/daemon.c` against the host `libsqlite3`, so **the C core must stay free of Qt and device headers**. `daemon.c` is in there for `daemon_alive()`, which decides whether the day gets measured at all: `pidfile_path()` and `proc_dir_path()` are overridable by environment variable (`POCKETBOOK_STATISTICS_PIDFILE`, `POCKETBOOK_STATISTICS_PROC`) exactly so a test can hand it a pidfile and a fake `/proc` and check what it makes of them.

The tests build their own DBs under `/tmp` and hand the paths straight to `tracker_init` — they never touch `daemon.c`. The device paths are overridable separately: `stats_db_path()` / `explorer_db_path()` honour `POCKETBOOK_STATISTICS_DB` / `POCKETBOOK_STATISTICS_EXPLORER_DB`, which is how a host build is pointed at a copy of a real device's databases.

`make test` compiles only `tracker.c`, `stats_db.c`, `version.c`, `log.c` and `daemon.c`, so **most of the code has no host compile at all** — `daemon.c`, `log.c`, everything in `qt/src/` and the QML are first built by CI. A new C file, or one that gained a call, is worth a five-second `cc -c -O2 -Wall -Wextra -std=gnu99 src/<file>.c -o /dev/null` before pushing; for the Qt sources there is nothing but the cross-build.

**Startup is ~3.2 s on a PB629, and it has been measured — do not guess at it again.** From `/proc/self/stat` against `/proc/uptime` and marks through `main()`: loader 0.13–0.44 s, InkView screen 0.1 s, launcher registration 0.01 s, `QGuiApplication` 0.07 s, `engine.load()` returning at ~3.0 s, first frame ~0.2 s later. Every bridge call the tabs make on load is under 100 ms, so the data is not it. `engine.load()` covers both compiling the QML and building the object tree, and the disk cache in `main.cpp` (`QML_FORCE_DISK_CACHE`, needed because QML from a resource is not cached by default) moved nothing — which leaves the tree: three tabs are constructed at startup, calendar included, with 31 cells and their covers. The lever, if it is ever worth pulling, is building a tab when it is first shown rather than at launch.

There is no host-runnable UI: the QML imports `com.pocketbook.controls`, which exists only in the device firmware at `/ebrmain/qml`. UI changes can only be verified on a reader — in practice from a screenshot the reader writes to `screens/scrNNNN.bmp` on its own storage. Measure it rather than eyeballing it when the question is a size or a margin: convert with `sips -s format png`, then decode the PNG in plain Python (zlib + the five filters; Pillow is not installed) and take bounding boxes of the dark pixels. That is how the firmware's own header button was matched — 38 px glyph, 2 px stroke, 27 px from the edge on a 758x1024 PB629, where `Global.dp(1)` measures ~1.32 px.

`make qt` needs Docker, which this machine does not have: the device binary is built in CI, not locally. So a change that has to reach the reader ships as one commit that bumps `VERSION`, then a `vX.Y.Z` tag pushed after it — CI cross-compiles, checks the tag against `VERSION` and publishes `PocketBookStatistics.zip`, and the reader picks it up from the About screen. `gh run watch <id> --exit-status` is the wait; nothing else here proves the C++ still compiles for ARM.

A change to the SQL that reads the firmware library is worth running against a copy of a real `explorer-3.db` with the `sqlite3` CLI before it is built — the schema is documented in `docs/DEVICE-DATA.md`, but only real data shows that a query returns 5 books and not 223, or that a ring reads 0 % on a shelf that has clearly been read.

CI (`.github/workflows/build.yml`) runs `make test` on a plain runner, then in the SDK image runs `qmllint qt/qml/*.qml` before `make qt`. `make test` also runs `tools/check_qml.py`, which catches what qmllint accepts and the engine then rejects — a duplicated function or id, or a property named after one the base type already has, makes the component fail to instantiate, `main.cpp` exits on an empty scene, and the app simply stops opening with no message anywhere. That last one shipped: `property var y` on an `Item` is "Cannot override FINAL property", which took down every file importing that type, and qmllint says it as a warning while only its exit code gates the build. **A property on an Item may not be called `x`, `y`, `z`, `width`, `height`, `state`, `data`, `parent`, `opacity`, `visible`, `enabled`, `anchors`, `clip`, `focus` or their neighbours** — the checker now holds the list. `rcc` embeds QML verbatim, so **the lint gate is the only pre-device check for QML syntax errors** — only its exit code matters; its import/unqualified-access warnings are noise because the firmware modules aren't resolvable off-device. Pushing a `v*` tag also publishes `PocketBookStatistics.zip` as a release.

## Architecture

One ARM ELF that is both the app and its background daemon; it links the device's own Qt 6.8.2 from `/ebrmain` (nothing Qt is bundled). SQLite and miniz *are* bundled: `CMakeLists.txt` compiles the `qt/third_party` amalgamations into the binary (`SQLITE_OMIT_LOAD_EXTENSION`, `SQLITE_THREADSAFE=1`), while `make test` links the host's `-lsqlite3` — the device and the host tests run different SQLite builds, so a passing test does not prove a version-specific feature exists on the reader.

**Data flow:** firmware library DB (`explorer-3.db`, opened **read-only**, never written) → `tracker.c` derives sessions → own stats DB (`/mnt/ext1/system/pocketbook-statistics/statistics.db`) → `stats_db.c` aggregates → `stats_bridge.cpp` shapes `QVariantMap`s → QML tabs.

**Layers:**
- `src/*.c` — plain C, no Qt. `tracker.c` (session derivation + schema + idempotent migration), `stats_db.c` (aggregation SQL), `daemon.c` (pidfile, 30 s poll loop, `spawn_daemon`).
- `qt/src/main.cpp` — `--daemon` is handled **before any Qt call** and runs the pure C loop; otherwise sets QPA `pocketbook2` + software rendering, registers the launcher icon, forks the daemon, loads `qrc:/main.qml`.
- `qt/src/stats_bridge.cpp` — the only QML-visible object (`stats` context property); each `Q_INVOKABLE` opens/closes explorer-3 itself. The entire QML↔C++ surface is seven calls — `overall()`, `currentBook()`, `month(year, mon)`, `year(y)`, `openBook(path)`, `setTotalHours(h)` and `setBooksFinished(n)` — with `catchUp()` private and run inside each of the four aggregates. The two setters take what the card should show and store the difference from the measurement as an offset in `meta`; a negative argument clears it. `year()` is the streak screen's whole feed: one entry per day from 1 January (0 not read, 1 read), the current and best runs, and where measurement begins. A day is read or it is not — the grid carried the firmware's finish marks as a third symbol until it turned out to say nothing the other two do not. `openBook()` is the one that measures nothing: it hands a path to the firmware's `OpenBook` (via `inkview_bridge.cpp`, `dlsym`-resolved like everything else there) so the Overview's cover and title lead back into the reader. The path it takes comes from `currentBook().filePath`, which is filled only while the file is still on the device — `files` is an inventory of what exists right now, and a PocketBook Cloud row carries no folder at all, so the lookup checks the folder and then the disk. `month()` returns a whole month in one map: `days[]` carrying that day's `secs` and a `books[]` with cover URLs, plus `readDays`, so the calendar grid, the day panel and the “+n” badge are all fed by that single call.
- `qt/src/inkview_bridge.cpp` — the **only** TU allowed to include `inkview.h`; its macros collide with Qt. Also holds the two network calls (Wi-Fi up, download-to-file).
- `qt/src/updater.cpp` — the `updater` context property: version check against the GitHub release, unpack, stage, hand over.
- `qt/qml/` — two screens, no scrolling (e-ink): `OverviewTab` — three sections, each a heading over a rule and a row of framed cards (current book / today / all books) — and `CalendarTab`, chosen from a bottom bar of equal icon-over-label cells in `main.qml`. `AboutTab` is not one of them: its glyph sits in the header opposite the firmware's home button and toggles back to the screen you came from, because an update check is a detour rather than a screen. The streak card on it is also a door: tapping it opens `StreakTab`, the year as a grid of squares (weekdays down, weeks across, split January-June over July-December because 53 weeks across 758 px leaves an 11 px square), built by a `Loader` when first opened rather than at startup — three tabs already are, and that is most of the ~3.2 s launch. It opens with the one thing there that is about the reading rather than the app — the streak, days in a row from `overall().streakDays`, the figure set in the Overview's serif at figure size while the words around it stay body text (the sentence is split on a marker passed through `Tr.t`, because word order differs per language and Turkish opens with the number). Under it sits the Overview's own section heading, a caption over a rule, so the two screens read as one app. The card is hidden below two days, because "1 day in a row" is not a run and that screen has no room to spare (it has painted over the navigation bar once). A day counts toward it at a minute or more, today may be empty without breaking it (the walk starts at yesterday, or a streak would read as broken every morning), and untracked days cannot count at all. Over the calendar sit two panels rather than screens: tapping a day opens `PanelDialog` with that day's breakdown, and tapping a book inside it opens `BookDialog` — the README's third screenshot is that day panel, not a tab. Shared pieces: `NavIcon.qml` (line art drawn on a Canvas — the firmware fonts have no dingbats to rely on) and the `Tr` i18n singleton. The Overview's own `Card` and `StatCard` are inline components: a card's width is derived (`(content - gap) / 2`), never placed, so a row cannot come out lopsided.

`docs/DEVICE-DATA.md` is the survey of what the firmware stores (both databases, their field coverage on a real device, the hash that joins them) and what it does not. Check it before designing a metric — it saves a USB round trip.

### The release loop

A device-side change is proved on the device, and the pull request is where that happens. **A build for the reader is published from a PR when it is asked for, never on every push**: put `[device]` in the commit message, or change `VERSION` in that commit, and that push goes out as `vX.Y.Z-prN` — a pre-release, so `/releases/latest` keeps answering with the last final version and only the reader carrying the `prerelease` marker is offered it. `VERSION` must also stand above the last release, or the reader would never be offered the build at all; when it does not, the run warns and publishes nothing. The suffix is `-pr`, not `-rc`: a candidate is aimed at a release, a PR build is whatever the branch was at when it was asked for. Both spellings share one counter, numbered from the tags that already exist for that version, and `version_compare()` orders them by that number alone (`2.1.0-pr7` is later than `2.1.0-rc3`; both lose to `2.1.0`). The workflow stamps the string into `VERSION` before the build, so the binary and the tag agree — a build stamped `2.1.0` would outrank every `2.1.0-prN` after it and refuse the next one. Cutting a candidate by hand still works: bump `VERSION` to `X.Y.Z-rcN` and push the tag. So: open the PR, ask for a build, install it on the one reader carrying the `prerelease` marker, look at what it did — screenshot, `app.log`, or the database over USB — and either fix and ask for the next build, or merge and tag `vX.Y.Z` — `VERSION` on the branch already says what that tag has to be. Builds pile up fast (v1.4.0 took eleven candidates, and that was before the asking was optional); when the final release goes out, delete the whole `-rc`/`-pr` run, releases and tags both, or the list becomes unreadable. Ordinary readers never see any of it: `/releases/latest` skips pre-releases.

### Invariants that are easy to break

- **`recovered = 1` rows are estimates, not measurements.** They are wall-clock spans reconstructed when the daemon wasn't running, capped at `RECOVERED_CAP_SECONDS`, and carry no `pages_start`. They count toward totals but must be excluded (`AND recovered = 0`) from every derived metric — averages, pages/min, session counts.
- **Sessions must not span local midnight, and that goes for a whole session written at once, not only for the gaps `tracker_observe` watches.** All day-level stats `GROUP BY date(end_time,'unixepoch','localtime')`, so one row is worth one day. The incremental path splits its own gap; `insert_session_split()` is the same rule for the two paths that place a session that had already run before anything saw it — the first observation of a session (the daemon is not scheduled while a book is on screen, so `catchUp()` is regularly the first to see one at all) and `tracker_recover()`. Until 1.6.3 neither split: reading 23:30 to 00:03 and then opening the app put all 33 minutes on the new day and left the previous one empty. The counted window is `[position_ts - active, position_ts]`, never the row's full span — a book reopened where it was left starts days before the seconds it credits — and `active` is capped at `RECOVERED_CAP_SECONDS`, so it can cross at most one midnight. The first row ends at midnight - 1 while holding the seconds up to midnight itself, which is the one second of slack in the migration's clamp. Rows already in the database are cut by `split_legacy_midnight()`, which runs once ever (a marker in `meta`, because `tracker_init` runs on every `catchUp()`) and moves seconds rather than inventing them; a later fix to it needs a new key.
- **Reading time is credited by one rule: a span of wall clock is worth only as much as the pages turned across it make plausible** (`credited()` in `tracker.c`). A flat cap cannot tell twenty unwatched minutes of reading from one page turned after an hour away, and paid ten minutes for both. So the bound is `pages x SECONDS_PER_PAGE_CAP` (300 s — the measured pace on a real device runs 28-137 s a page), falling back to `IDLE_CAP_SECONDS` (600) where there is no page evidence at all, and never exceeding `RECOVERED_CAP_SECONDS` (90 min) for a single unobserved stretch. A page *backwards* is a jump — to a bookmark, or back to re-read — and buys nothing; what is read forward from there is credited by the observations that follow.
- **A position is not a page count, and a big enough move is navigation.** Books that gather their footnotes at the back are read by tapping a link and tapping back, so `cpage` lands hundreds of pages away and returns; under `credited()` that distance vouches for the entire window, and as `pages_end - pages_start` it went into the pace as pages read — a real device reported over 7000 pages in a day (issue #2). `page_jump()` is the mirror of `credited()`: a forward move of at least `JUMP_MIN_PAGES` (10) that would need more than `SECONDS_PER_PAGE_MIN` (15 s) a page to be read costs the window its seconds *and* its pages, exactly as a move backwards already did. The floor is what keeps two saves seconds apart from disqualifying three genuinely turned pages. What is read from wherever the reader lands is credited by the observations that follow, and `pages_end` still tracks the real position — the way back would otherwise be measured from a page nobody is on.
- **The pace is built on `pages_read`, never on `pages_end - pages_start`.** Those two are positions and move by navigation; `pages_read` is accumulated per observation from what was believed as reading, is split at midnight along with the seconds, and stays 0 on `recovered` rows. Every aggregate that divides pages by minutes selects `pages_read > 0`. A database from before 1.6.5 has the column seeded once from the two positions (marker `pages_read_1_6_5` in `meta`) so an existing pace survives the upgrade; that backfill must stay one-shot, or every window that was all jump gets its distance handed back on the next open.
- **A position stamped before the open belongs to the session before it, and has to be paid there.** Switch the reader off inside a book and the firmware saves the position on the way down, then stamps a fresh `opentime` on the way up: `position_ts < opentime`. `tracker_observe()` clamps that away (a row must not end before it begins), which used to drop the whole stretch since the previous row's last observation — measured on a real device as 14 minutes and 10 turned pages arriving as a day with no reading at all, the pages inside the new zero-second window reading as a jump on top. `close_previous_session()` credits it to the row that was open at the time, under the ordinary rules (`credited()`, `page_jump()`, split at midnight through `credit_window()`), and `update_session()`'s `AND end_time<?1` is what stops a second tracker paying for it twice.
- **A live pid is not our pid.** The pidfile survives a reboot and pids come from a small range, so `kill(pid, 0)` alone called the daemon alive when the number belonged to some firmware process: nothing started a daemon, and the day was measured only while the app happened to be open. `daemon_alive()` and the shim both read `/proc/<pid>/cmdline` and require the app's name *and* `--daemon`; where there is no procfs (host tests) the pid alone still decides.
- **A tracker that has just been created must resume the session it finds, not start one beside it.** `resume_session()` adopts the open row for this `(book_id, opentime)` and its `end_time`/`pages_end` as the last known position. Every caller builds a fresh tracker sooner or later — the daemon after a restart, and `StatsBridge::catchUp()` on *every* refresh — and until 1.6.2 the stretch since the last observation was not capped but dropped: 18 minutes and 30 turned pages reached the screen as "1 minute". This is also what makes a dead daemon survivable: opening the app credits the whole stretch, split at midnight like any other.
- **Two trackers write the same session, so what has been credited is what the row says — never what a process remembers.** The daemon's tracker lives across polls; `catchUp()` builds a fresh one on every refresh, and the app's minute timer keeps firing behind the reader because `Qt.application.state` never leaves `Active` on this firmware. Until 1.6.2-rc4 each measured the gap from its own last-seen `position_ts` and both billed it: three sessions in one evening carried exactly twice the wall clock they spanned, and a 92-minute afternoon reported 106. `tracker_observe()` re-reads the open row on *every* observation (not only on a session change), and `update_session` carries `AND end_time<?1` so the loser of a race adds nothing instead of adding it twice. The migration clamps any non-recovered row to its own span — an hour of reading can never be worth more than the hour it spanned.
- **`tracker_recover()` must not touch the session that is open right now.** It runs at daemon start, and the shim starts the daemon seconds after a book is opened; whether a page had been turned by then decided whether the evening was stamped `recovered = 1` and dropped from every average. The book `tracker_read_state()` returns is the one about to be measured, so it is skipped — `books_settings` keeps only the latest open per book, which makes the newest of them the only one that can still be running.
- **The daemon is not scheduled while a book is on screen, so reading time can only be measured from the firmware's `position_ts` — never by counting our own polls.** The CPU suspends between page turns: a 20-minute stretch got 9 of the 41 polls it was owed, an 18-minute one got 3. 1.6.2-rc2 credited the poll interval itself whenever the firmware's reader had a process, on the theory that a book on screen is a book being read, and recorded a 45-minute evening as 9 minutes. The premise was wrong in the other direction too: `eink-reader` stays resident after the book is closed, so a tick landed on a ten-hour-old session while the user was in this app. `position_ts` is stamped whether or not our process has a processor, which makes it the one clock here that does not depend on being scheduled — but it is **not** a page turn. The firmware writes it when the reader saves state, which on a PB629 measured out at once every 15 to 75 minutes: 64 pages across an evening arrived as five observations. So a single window between two saves routinely holds both the reading and the hours the reader lay closed, and no threshold on `position_ts` alone can separate them. The cap is what a stretch the daemon missed costs: ten minutes, however long it really was. The daemon's heartbeat prints polls against wall seconds *and* awake seconds, so the duty cycle stays on record.
- **Wall clock is not reading time, and the two clocks are what tell them apart.** `CLOCK_MONOTONIC` stops while the device is suspended and `time()` does not, so the difference across one poll interval is exactly what the CPU slept through — during which nobody turned a page. `note_sleep()` in `tracker.c` accumulates only stretches over `DEEP_SLEEP_SECONDS` (15 min) into `meta.sleep_total`, because the e-ink reader also drops the CPU between renders while a book is genuinely being read: the poll intervals measured mid-reading run 2-7 minutes of wall clock at a 7-22 % duty cycle, and a closed cover runs far longer. Each session row carries `sleep_end`, the total as of its `end_time`, and the next observation subtracts the difference from the window before `credited()` weighs the pages. Two rules hold it up: only marks **one poll apart** are classified — `StatsBridge::catchUp()` looks hours after the last mark, and a difference measured across an afternoon says nothing about where inside it the device slept — and the total is written to flash only when it grows, never once per poll. Without this, an evening of 18:00 to 21:25 with 64 pages billed 3 h 15 m: five windows, each under its own page budget, each mostly a shut cover.
- **The two all-time figures may be set by hand, and that offset lives in `meta` — never in a session row.** Reading done before the app was installed, or on another reader, is invisible to it, so a long press on the *books finished* or *total hours* card opens a step dialog and `manual_offset_books` / `manual_offset_seconds` hold the difference from the measured figure (which is why later reading still adds to the total). They are added in exactly where those two cards are built, in `overall()`, and nowhere else: the pace, today's minutes, the calendar, the day panel and the streak stay measurements. Writing them into `sessions` instead would move every one of those.
- **The Overview shows measurement, not inference.** It once carried a ring for "how much of the shelf on this device have I read", derived from `files` joined to `books_settings`; it was removed in 1.6.0 along with the query behind it — the only thing that screen asked the firmware library. What is left is today's minutes, the measured pace, books finished (from the firmware's own flag) and total hours. Two figures on that screen answer different questions and must not be reconciled: the finished count is all-time, from `completed_ts`, and includes books long deleted, while anything about the current shelf would drop as soon as new books are copied on (26 finished ever ÷ 5 books present is how a ratio once reported 100 %).
- **Deduplicate by title, not `book_id`.** `books_impl` keeps stale rows and the same book exists as several file copies; the calendar and book-count queries group by normalized title (see `sameBook()` / `titleWords()` prefix matching).
- **Nothing before `meta.tracking_since` may be shown as history.** The marker is stamped on first run; earlier sessions only exist because `tracker_recover()` reconstructed them from the firmware's last-open timestamps, and they are guesses, not measurement. Every session aggregate appends `AND_TRACKED` (`src/stats_db.h`), and the calendar renders those days as unknown via `trackedFromDay` rather than as "not read". Firmware-sourced finish dates are exempt — the calendar draws them for untracked days too, carrying no reading time (`secs = 0`), because the firmware dates the finish without saying how long that day's reading was. A screen that can show a blank day must also say why it is blank: the calendar dims untracked day numbers and prints `trackingSince` beneath the grid, so an empty month reads as "not recorded yet" rather than as a bug.
- **"Finished" always comes from the firmware** (`books_settings.completed` / `completed_ts`), never from our own DB, so it matches the Library UI.
- **`VERSION` is the single source of the version, and a release tag must match it.** It is read by CMake into `APP_VERSION` and compared against the release's `tag_name` (`version_compare` in `src/version.c`, host-tested). A tag that disagrees with the file makes every installed build offer an update to the version it already runs — CI fails the tag build for exactly that reason. Bump `VERSION` in the commit that earns the release, not at tag time.
- **Release candidates ship to one device, by a marker file.** A tag containing `-rc` is published by CI as a GitHub pre-release, which `/releases/latest` ignores — so every ordinary reader keeps seeing the last final version. A device with `system/pocketbook-statistics/prerelease` present makes `updater.cpp` ask for the release *list* instead. **That list is ordered by tag name as text, not by date** — `rc9, rc8 … rc2, rc11, rc10, rc1` — so the newest entry is not the first one; the updater compares every non-draft tag and keeps the highest. Nothing in the app creates that file; it is placed by hand over USB. `version_compare` orders `1.4.0-rc1 < 1.4.0-rc2 < 1.4.0`, which is what lets one candidate replace another; `VERSION` must carry the suffix too, since CI checks the tag against it.
- **A running binary cannot overwrite itself.** The updater unpacks to `PocketBookStatistics.app.new` beside the installed file and leaves the swap to a generated `/bin/sh` script that waits for the app's PID to disappear, kills the daemon (it runs from the same ELF), `mv`s the file and starts the new one. Staging must stay on the same mount — `mv` is only atomic within one filesystem, and `/mnt/ext1` is not the same one as `/tmp`.
- **The update path never blocks on the network without repainting first.** InkView must not be driven from a second thread, so `check()`/`install()` run on the GUI thread and call `publish()` (state + `processEvents`) before each blocking firmware call. User input stays excluded there so a second tap cannot re-enter them.
- **Covers must outlive the book file.** Most finished books get deleted, and both the file and the firmware's cache entry go with them — so a thumbnail only exists later if it was copied while the book was still there. Three rules follow:
  - The cover key is the **bare file hash from `books_fast_hashes`**, never `files.fast_hash`: `files` lists only what is on disk (5 of 223 books on the reference device), so keying off it loses the cover for every deleted book. Rows written before v0.7 hold `<storageid><hash>` — 33 characters instead of 32, which is how `coverUrlForKey()` tells them apart.
  - `adopt_cover()` in `tracker.c` copies the firmware's PNG into `OWN_COVER_DIR` as `fw_<hash>.png` on first sight of a book. It runs in the poll path: no allocation, and a no-op once the copy exists.
  - Lookup order in `resolveCoverUrl()` is our cache → extraction from the file (`book_cover.cpp`, miniz) → firmware cache, adopted on the way out. Extraction wins over the firmware cache because the cache holds ad pages instead of the cover for some Calibre books; our cache wins over both because it is the only one that survives. `book_cover.cpp` tells the formats apart by what is *inside* the file, not by its extension: `META-INF/container.xml` means EPUB and the OPF alone decides (guessing at an image inside an EPUB finds chapter illustrations), an `.fb2` member means an fb2.zip, and any other archive of images is a comic whose cover is its first page in natural order (`page2` before `page10`). A bare `.fb2` is scanned as bytes rather than parsed as XML — half of them are windows-1251 and Qt 6 has no codec for that, while the base64 in `<binary>` is ASCII either way. Only the `.fb2` suffix opens a non-archive: reading every 20 MB PDF into RAM on each refresh, to look for XML that is not there, costs as much as an extraction and never finds one. PDF, DJVU, MOBI and CBR have no decoder here and stay on the firmware cache.

### Device-side constraints

- Cross-compilation constraints (softfp ABI, exact Qt version match, `rcc --no-zstd`) come from the SDK — see the fstanis/pocketbook-sdk-qt6 notes before touching the toolchain or CMake.
- **The launcher icons are 106x64 8-bit BMPs, and the width is the load-bearing half.** The launcher draws a tile as image-then-label at the bitmap's native size, so the canvas height decides where the label sits — a 128 px canvas drops the label below the row of labels beside it. Width is stranger: 106 renders, 48 makes the icon vanish entirely (the tile shows no image at all and the label slides up into the empty space), and why has never been established, so treat 106 as the only known-good value. Both sizes were confirmed on a PB629; `--canvas`/`--glyph` on `tools/make_icon.py` exist for re-probing them. The glyph itself lives on a 48-unit grid scaled onto the canvas, with the stroke width left unscaled so the line art stays as thin as the firmware's own icons (~50 px glyphs) instead of reading as heavier than its neighbours.
- **Nothing of ours starts at boot, and the shim is the way around it.** The firmware's autostart lives in `/ebrmain`, which is the firmware partition — out of reach and not worth touching. What *is* reachable: the firmware runs `/mnt/ext1/system/bin/<name>.app` for whichever application a format names in `system/config/extensions.cfg` (KOReader uses the same door). `shim.cpp` installs `pbstatistics-open.app` there and puts it at the *front* of the application list for epub/fb2/pdf, keeping the names already there so "open with" still offers them. The script starts the daemon and `exec`s the reader the table names next. Three rules it must keep: the pidfile is read in the shell (starting the app to ask costs a full Qt load and delayed the book by five seconds), the daemon start is delayed so it does not fight the reader for the flash, and every path above the handover is failure-tolerant — a shim that does not reach its last line is a book that will not open.
- The app writes outside its own directory in exactly one place: `installer.cpp` adds a `U_pocketbook_statistics` entry to `system/config/desktop/view.json` after backing it up. Keep that patch idempotent and failure-tolerant — the app must still start if the file is missing or read-only.
- **The app was called ReadTrack until v0.10.6, and nothing carries that name forward.** The rename (v0.11.0) moved the binary, the data directory, the release asset and the launcher entry; v0.11.0 shipped a one-shot migration for them, and v0.11.1 deleted it — the app has one user, who had already moved across. A device that still holds `system/readtrack` or a `U_readtrack` tile is not migrated by any current build: it starts a fresh history and leaves the old files where they are.
- **The network is used in exactly one place: the update check.** `updater.cpp` asks `api.github.com` for the latest release and downloads that release's `PocketBookStatistics.zip`, and only when the user presses the button on the About tab — there is no background check and no other host is ever contacted. Reading data never leaves the device.
- **The firmware's network API behaves differently from what `inkview.h` promises**, and all three lessons were paid for on a PB629:
  - **The session API (`NewSession`/`DownloadTo`) does not transfer anything under Qt.** It returns `NET_OK` and writes a zero-byte file: the transfer is handed to the event loop InkView runs for its own applications, and ours is Qt's. Use the synchronous `QuickDownloadExt3`, which returns the whole body in one heap buffer.
  - **`iv_sessioninfo` does not match the header on this firmware.** Reading `->response` yielded 1 and 0 where an HTTP status belonged and killed the process. Judge a download by what landed in the file; never read a session struct.
  - **Redirects are followed for us.** A release asset URL bounces to a CDN host, and `QuickDownloadExt3` lands the final body — confirmed on a PB629 with the 599 KB zip. Nothing needs to chase a `Location` header (which is just as well: the session struct it would come from is unreadable).
  - **Every transfer blocks the UI thread, so the timeout is a UI decision.** `inkViewDownload` takes both the timeout and whether to retry from the caller: the version check gets `kCheckTimeoutSeconds` (20) and no retry, the release gets `kDownloadTimeoutSeconds` (60) and one retry after a reconnect. Associated-but-offline — a captive portal, a router with no uplink — passes the connection test and then runs into the timeout, and with a retry it used to freeze the screen for two minutes to say what one attempt says.
  - **`QueryNetwork()` is not a connection test.** `0x202` (`NET_WIFI|NET_WIFIREADY`) means the radio is up and answered a scan — a download in that state comes back empty. Always call `NetConnectSilent(NULL)`, which is a no-op when a connection exists.
- **Everything in the network path is resolved with `dlsym`, never linked.** `inkview.h` is the SDK's, `libinkview.so` is the device's, and a function present in the header but missing from the library is a lazily-bound symbol that kills the process on first call — with no console to say why. `resolve<Fn>()` in `inkview_bridge.cpp` turns that into a log line and a fallback.
- **`system/pocketbook-statistics/app.log` is the only debugger this app has.** `src/log.c` is the one writer — the daemon has no Qt, so the C side owns it and `update_log.cpp` is a thin bridge onto it. Every line is opened, written and closed on its own so a crash cannot swallow the last one, and the file is halved rather than deleted at 64 KB, keeping the newest 32 KB. The About tab shows its tail when an update run ends in `error` — and only then: the screen does not scroll, so anything printed under a successful check falls off the bottom unseen. Log events that would matter a week later — starts, stops, refusals, anything that failed — and trace a new device-side path this way rather than making another USB round trip; but do not narrate normal work, or the week's worth of signal drowns.

### Before pushing

Read the diff back before committing it, as a reviewer would — not the intent, the lines. Every one of these shipped as a release and had to be fixed by the next one:

- **Check the change against the invariants above.** Rows of estimated reading time were written at 1–5 hours each; `tracker_init` rewrites any recovered row over 90 minutes on every open, so 265 h became 172.8 h at the next launch.
- **Ask whether the change can reach the device at all.** The shim script is copied to `system/bin` at install and nothing rewrote it afterwards, so two releases of fixes to it never left the repository. Then the refresh that fixed *that* keyed off `installed()`, which demands an entry per format — skipping exactly the hand-set-up device it was written for.
- **Do the arithmetic instead of eyeballing the layout.** A spacer was added beside a Row that already applies `spacing`, and the figures row came out 21 px wider than the screen; the label lost its last letter. `Global.dp(1)` ≈ 1.32 px on a PB629 — the numbers are checkable before the build.
- **Verify assumptions about the outside world.** GitHub returns `/releases` sorted by tag name as text, not by date, so the updater's "newest is first" put a device on rc9 in front of rc9.
- **Run `make test`** (tracker asserts + `check_qml.py`), and `cc -c` any C file the host tests do not compile. CI is the only thing that compiles `qt/src/`, so a push is the first real check of C++ — which is a reason to re-read it, not to lean on the runner.

### Conventions

- New source files must be added to `CMakeLists.txt`; new QML files to **both** `qt/qml/pocketbook-statistics.qrc` and the parent tab.
- The launcher tile's label is the **one** user-facing string outside the catalogs: `launcherTitle()` in `installer.cpp` picks it from the device language, because it is written into `view.json` before a QML engine exists. Adding a language means touching that table too. The label is "Statistics"/"Статистика"/"Statistik", not the app name — it sits among firmware tiles that are named for what they do.
- All other user-facing strings go through `Tr.t("<key>")`, resolved against the 29 catalogs in `qt/qml/i18n/`; `Tr.plural("plural.<noun>", n)` inflects a noun for a count. A missing key falls back to English, then renders as the key itself. Adding a language never touches a call site: write the catalog, list it in `pocketbook-statistics.qrc`, add an import and a row to the `catalogs` table in `Tr.qml`, and a row to `kLauncherNames` in `installer.cpp`. Each catalog carries its own `plural(n)`; the form arrays must be long enough for the largest index it returns (Slovenian needs four).
- **`GlobalValues.defaultBorderColor` is black on this firmware.** It is a line colour, not a tint: filling a shape with it and then drawing on top in `defaultTextColor` produces a black rectangle, which is how the progress bar and the "ALL BOOKS" heading both disappeared. For an empty track or a wash, use `defaultTextColor` at low opacity instead.
- Sizing and color come from the firmware theme: `Global.dp(n)`, `GlobalValues.*`, `FontStyles.*`, `StyledText` instead of `Text`. No hardcoded pixels or colors, so dark/light follows the device.
- Tabs refresh in `Component.onCompleted` and `onVisibleChanged`, and `main.qml` adds two more: when the application becomes active again (returning from the reader is neither of the first two — the window never stopped being visible) and once a minute while it is in front. There is no live binding to the DB. Every `StatsBridge` aggregate calls `catchUp()` first, which runs one `tracker_observe` on the spot: the daemon's 30 s poll is too coarse for "close the book, open the app", and a daemon that was killed while the reader had the foreground would otherwise leave that session unwritten until the next launch. Anything new that reads the stats DB for the UI must go through it too.
- C code is `-Wall -Wextra -std=gnu99`, no allocation in the poll path; existing comments are English (a few older ones German).
